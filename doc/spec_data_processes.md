# LifePIM Desktop — Data Processes and Logger JSON Import

## 1. Objective

Enhance the LifePIM Desktop **Data** tab with a new **Processes** area for managing repeatable data-processing operations.

The first implemented process type will import raw JSON files generated by the LifePIM Logger mobile app into a separate SQLite database.

The design must be reusable for future processes such as:

* Normalising logger records.
* Building activity periods.
* Generating calendar event candidates.
* Importing CSV files.
* Extracting media metadata.
* Rebuilding file indexes.
* Processing financial or health exports.
* Generating thumbnails.
* Running saved database transformations.

Do not build a general visual ETL designer, arbitrary workflow language, or drag-and-drop pipeline builder.

The first version should use:

> Saved process definition → built-in process handler → output database → run history

---

# 2. High-level design

Add a reusable process framework to LifePIM Desktop.

A process consists of:

1. A saved process definition.
2. A known process type.
3. Process-specific configuration.
4. A built-in handler that performs the work.
5. Run history.
6. File-level processing history.
7. Informational, warning and error messages.

For the logger import:

```text
Logger JSON folder
    ↓
logger_json_import process handler
    ↓
Separate logger SQLite database
    ↓
Raw logger tables
    ↓
Process run and file history
```

LifePIM should own:

* Process definitions.
* Configuration.
* User interface.
* Run history.
* Status reporting.
* File tracking.
* Execution controls.

The logger handler should own:

* Logger JSON recognition.
* JSON parsing.
* Schema validation.
* Record extraction.
* Target-table selection.
* Database insertion.
* Logger-specific errors and warnings.

# 4. Terminology

Use the following terminology consistently:

## Process

A saved, repeatable operation performed by LifePIM.

Examples:

* Import Logger JSON.
* Normalise Logger Data.
* Build Activity Periods.
* Generate Calendar Candidates.

## Process type

The registered implementation used to execute the process.

Initial process type:

```text
logger_json_import
```

## Process run

One execution of a saved process.

## Process file

A source file discovered or processed by a process.

## Handler

The Python implementation associated with a process type.

## Preview

A read-only scan that validates configuration and reports what would happen without modifying the target database or source files.

## Rebuild

Delete and recreate the process-owned logger database tables, then import all available recognised source files again.

# 7. Main LifePIM database schema

Store process definitions and execution history in the normal LifePIM application database.

Use the project’s existing primary-key type and timestamp conventions.

All execution timestamps should be stored in UTC.

## 7.1 `lp_process`

Stores the saved process definition.

```sql
CREATE TABLE lp_process (
    process_id              INTEGER PRIMARY KEY,
    process_name            TEXT NOT NULL,
    process_type            TEXT NOT NULL,
    description             TEXT,
    is_enabled              INTEGER NOT NULL DEFAULT 1,
    configuration_json      TEXT NOT NULL,
    created_at_utc          TEXT NOT NULL,
    updated_at_utc          TEXT NOT NULL
);
```

Recommended indexes:

```sql
CREATE INDEX ix_lp_process_type
    ON lp_process(process_type);

CREATE INDEX ix_lp_process_enabled
    ON lp_process(is_enabled);
```

Rules:

* `process_name` must be user-readable.
* `process_type` identifies the registered handler.
* `configuration_json` contains handler-specific configuration.
* Unknown process types must remain visible but cannot be executed.
* Disabling a process prevents normal execution but does not delete its history.
* Rebuild may still require an explicit user action and should not run automatically.

---

## 7.2 `lp_process_run`

Stores one execution of a process.

```sql
CREATE TABLE lp_process_run (
    process_run_id          INTEGER PRIMARY KEY,
    process_id              INTEGER NOT NULL,
    started_at_utc          TEXT NOT NULL,
    finished_at_utc         TEXT,
    status                  TEXT NOT NULL,
    trigger_type            TEXT NOT NULL,
    run_mode                TEXT NOT NULL,

    files_found             INTEGER NOT NULL DEFAULT 0,
    files_processed         INTEGER NOT NULL DEFAULT 0,
    files_skipped           INTEGER NOT NULL DEFAULT 0,
    files_failed            INTEGER NOT NULL DEFAULT 0,

    records_read            INTEGER NOT NULL DEFAULT 0,
    records_written         INTEGER NOT NULL DEFAULT 0,
    records_skipped         INTEGER NOT NULL DEFAULT 0,
    records_failed          INTEGER NOT NULL DEFAULT 0,

    summary                 TEXT,
    error_message           TEXT,

    FOREIGN KEY (process_id)
        REFERENCES lp_process(process_id)
);
```

Allowed `status` values:

```text
pending
running
success
warning
failed
cancelled
```

Allowed `trigger_type` values for Version 1:

```text
manual
admin_shortcut
startup
```

Allowed `run_mode` values:

```text
preview
incremental
rebuild
```

Rules:

* Create the run record before processing begins.
* Set status to `running` before scanning source files.
* Always attempt to set a terminal status.
* A run with some successful files and some failed files should normally finish as `warning`.
* A run that cannot start, open its target database or process any files should finish as `failed`.
* A run with no new files may finish as `success` with a clear summary.

Recommended indexes:

```sql
CREATE INDEX ix_lp_process_run_process
    ON lp_process_run(process_id, started_at_utc DESC);

CREATE INDEX ix_lp_process_run_status
    ON lp_process_run(status);
```

---

## 7.3 `lp_process_run_message`

Stores structured execution messages.

```sql
CREATE TABLE lp_process_run_message (
    process_run_message_id  INTEGER PRIMARY KEY,
    process_run_id          INTEGER NOT NULL,
    message_time_utc        TEXT NOT NULL,
    message_level           TEXT NOT NULL,
    message_code            TEXT,
    message_text            TEXT NOT NULL,
    context_json            TEXT,

    FOREIGN KEY (process_run_id)
        REFERENCES lp_process_run(process_run_id)
);
```

Allowed message levels:

```text
debug
info
warning
error
```

Example messages:

```text
INFO     SOURCE_SCAN_STARTED
         Scanning configured logger source folder.

INFO     FILE_IMPORTED
         Imported app_usage_20260806_221500.json.

WARNING  UNKNOWN_RECORD_TYPE
         File contains an unsupported record type.

ERROR    INVALID_JSON
         JSON parsing failed at line 184.
```

`context_json` may include:

```json
{
  "source_path": "D:\\LifePIM\\Logger\\incoming\\example.json",
  "record_type": "app_usage",
  "line_number": 184
}
```

Do not store Python stack traces as the only user-facing error. Stack traces may be logged to the normal application log, while this table receives a clear summary.

## 7.4 `lp_process_file`

Stores the durable processing history of each source file.

```sql
CREATE TABLE lp_process_file (
    process_file_id         INTEGER PRIMARY KEY,
    process_id              INTEGER NOT NULL,

    source_path             TEXT NOT NULL,
    source_path_normalised  TEXT NOT NULL,
    file_name               TEXT NOT NULL,
    file_size_bytes         INTEGER,
    file_modified_at_utc    TEXT,
    file_hash               TEXT,

    first_seen_at_utc       TEXT NOT NULL,
    last_seen_at_utc        TEXT NOT NULL,
    last_processed_at_utc   TEXT,

    last_process_run_id     INTEGER,
    status                  TEXT NOT NULL,

    detected_file_type      TEXT,
    detected_record_types   TEXT,

    records_read            INTEGER NOT NULL DEFAULT 0,
    records_written         INTEGER NOT NULL DEFAULT 0,
    records_skipped         INTEGER NOT NULL DEFAULT 0,
    records_failed          INTEGER NOT NULL DEFAULT 0,

    error_message           TEXT,

    FOREIGN KEY (process_id)
        REFERENCES lp_process(process_id),

    FOREIGN KEY (last_process_run_id)
        REFERENCES lp_process_run(process_run_id)
);
```

Allowed status values:

```text
discovered
imported
skipped
warning
failed
missing
```

Recommended indexes:

```sql
CREATE INDEX ix_lp_process_file_process
    ON lp_process_file(process_id);

CREATE INDEX ix_lp_process_file_identity
    ON lp_process_file(
        process_id,
        source_path_normalised,
        file_size_bytes,
        file_modified_at_utc
    );

CREATE INDEX ix_lp_process_file_hash
    ON lp_process_file(process_id, file_hash);
```

Do not rely on filename alone for duplicate detection.

## 7.5 Optional `lp_process_run_file`

Add a run-to-file history table if this fits the current data-access style.

This is strongly recommended because `lp_process_file` only stores the latest state.

```sql
CREATE TABLE lp_process_run_file (
    process_run_file_id     INTEGER PRIMARY KEY,
    process_run_id          INTEGER NOT NULL,
    process_file_id         INTEGER,
    source_path             TEXT NOT NULL,
    status                  TEXT NOT NULL,

    records_read            INTEGER NOT NULL DEFAULT 0,
    records_written         INTEGER NOT NULL DEFAULT 0,
    records_skipped         INTEGER NOT NULL DEFAULT 0,
    records_failed          INTEGER NOT NULL DEFAULT 0,

    started_at_utc          TEXT,
    finished_at_utc         TEXT,
    message                 TEXT,

    FOREIGN KEY (process_run_id)
        REFERENCES lp_process_run(process_run_id),

    FOREIGN KEY (process_file_id)
        REFERENCES lp_process_file(process_file_id)
);
```

This table should be implemented in Version 1 unless it conflicts materially with the existing architecture.

It allows a user to open an old run and see exactly which files were processed during that run.

# 8. Process configuration

The initial process must use:

```text
process_type = logger_json_import
```

Example configuration:

```json
{
  "source_folder": "D:\\LifePIM\\Logger\\incoming",
  "file_pattern": "*.json",
  "include_subfolders": true,

  "database_path": "<LIFEPIM_DATA>\\logger\\logger.sqlite",

  "import_mode": "incremental",
  "duplicate_detection": "metadata_and_hash",

  "successful_file_action": "leave",
  "processed_folder": null,

  "invalid_file_action": "leave",
  "failed_folder": null,

  "hash_algorithm": "sha256",
  "calculate_hash_during_preview": false,

  "create_database_if_missing": true,
  "create_tables_if_missing": true,

  "allow_unknown_record_types": true,
  "stop_on_file_error": false
}
```

Supported `successful_file_action` values:

```text
leave
move
```

Do not implement automatic source-file deletion.

Supported duplicate-detection modes:

```text
metadata
metadata_and_hash
hash
```

Recommended default:

```text
metadata_and_hash
```

Expected behaviour:

1. Use normalised path, file size and modified timestamp for a quick initial comparison.
2. Calculate a SHA-256 hash where needed.
3. Treat a file with the same content hash as already imported even if it has moved or been renamed.
4. Treat a changed file as a new file version requiring processing.
5. Never silently overwrite an earlier process-file history record without preserving the current run history.

# 10. Process handler interface

Create a reusable base interface.

Exact implementation may use an abstract base class, protocol or equivalent project convention.

```python
class ProcessHandler:
    process_type: str

    def get_definition(self) -> ProcessTypeDefinition:
        """
        Return display name, description, supported operations,
        configuration schema and default configuration.
        """

    def validate_config(
        self,
        config: dict
    ) -> ValidationResult:
        """
        Validate the saved configuration without modifying data.
        """

    def preview(
        self,
        config: dict,
        context: ProcessRunContext
    ) -> ProcessPreviewResult:
        """
        Scan source data and report what would happen.
        Must not modify source files or target data.
        """

    def run(
        self,
        config: dict,
        context: ProcessRunContext
    ) -> ProcessRunResult:
        """
        Execute an incremental process run.
        """

    def rebuild(
        self,
        config: dict,
        context: ProcessRunContext
    ) -> ProcessRunResult:
        """
        Safely rebuild process-owned output data.
        """
```

The context should provide controlled methods such as:

```python
context.info(...)
context.warning(...)
context.error(...)
context.update_progress(...)
context.register_file(...)
context.update_file_result(...)
context.check_cancelled()
```

Handlers should not update process framework tables directly where avoidable. Use a process service or run context so execution bookkeeping is consistent.

# 12. Process service

Create a common service responsible for process execution.

Recommended responsibilities:

```text
ProcessService
├── create_process
├── update_process
├── validate_process
├── preview_process
├── run_process
├── rebuild_process
├── cancel_process
├── get_process
├── list_processes
├── list_runs
├── get_run_details
└── list_run_files
```

The service must:

1. Load the process definition.
2. Check that the process is enabled where appropriate.
3. Resolve its registered handler.
4. Parse and validate `configuration_json`.
5. Create the run record.
6. Invoke the handler.
7. Persist progress and messages.
8. Persist file-level results.
9. Finalise counts and status.
10. Handle exceptions safely.
11. Write unexpected exception details to the application log.
12. Return a structured result to the UI.

Prevent two simultaneous runs of the same process in Version 1.

A process already marked `running` should show:

```text
This process is already running.
```

Also recover sensibly from an application crash that leaves a stale run marked as `running`.

On application startup, runs still marked `running` from a previous application session may be changed to:

```text
failed
```

with a summary such as:

```text
The application closed before this process completed.
```

# 13. Separate logger database

Create or maintain a separate SQLite database for imported logger data.

Default location:

```text
<LifePIM data directory>/logger/logger.sqlite
```

Do not store the potentially large raw logger records in the primary LifePIM database.

The primary LifePIM database stores:

* Process definitions.
* Process runs.
* Process messages.
* Process-file history.

The logger database stores:

* Raw imported records.
* File ingestion metadata needed within the logger domain.
* Future cleaned and aggregate logger tables.

Use a logger database schema-version table:

```sql
CREATE TABLE logger_schema_version (
    schema_version          INTEGER NOT NULL,
    applied_at_utc          TEXT NOT NULL,
    description             TEXT
);
```

Use migrations rather than relying only on `CREATE TABLE IF NOT EXISTS`.

# 14. Logger database ingestion metadata

The logger database should contain its own source-file metadata so imported records remain traceable even if the main LifePIM database is restored separately.

Create:

```sql
CREATE TABLE logger_import_file (

    process_id              INTEGER,
    process_run_id          INTEGER,

    source_path             TEXT NOT NULL,
    source_file_name        TEXT NOT NULL,
    source_file_size        INTEGER,
    source_modified_at_utc  TEXT,
    source_file_hash        TEXT,

    imported_at_utc         TEXT NOT NULL,
    status                  TEXT NOT NULL,

    records_read            INTEGER NOT NULL DEFAULT 0,
    records_written         INTEGER NOT NULL DEFAULT 0,
    records_skipped         INTEGER NOT NULL DEFAULT 0,
    records_failed          INTEGER NOT NULL DEFAULT 0,

    error_message           TEXT
);
```

Each imported logger record should include, either directly or through a foreign key:

```text
logger_import_file_id
source_record_index
source_record_type
ingested_at_utc
```

This allows every row to be traced back to its source file and source position.

# 15. Raw logger tables

The importer should route recognised records to typed raw tables.

Use the actual JSON structures already produced by LifePIM Logger. Inspect the current files and existing `/src/logger/*` work before finalising the exact columns.

At minimum, support the known logger categories where present:

* App usage.
* Installed applications.
* Location samples.
* Device state.
* Battery state.
* Network state.
* Screen state.
* Barometer or pressure samples.
* Temperature samples.
* Sensor samples that are currently retained.
* Logger metadata or device metadata.

Recommended naming:

```text
raw_app_usage
raw_installed_app
raw_location
raw_device_state
raw_battery
raw_network
raw_screen_state
raw_pressure
raw_temperature
raw_sensor
raw_logger_metadata
raw_unknown_record
```

Do not force unrelated record types into one giant table.

Every raw table should include common ingestion columns:

```sql
logger_record_id        INTEGER PRIMARY KEY,
logger_import_file_id   INTEGER NOT NULL,
source_record_index     INTEGER,
source_timestamp_utc    TEXT,
ingested_at_utc         TEXT NOT NULL,
raw_record_json         TEXT
```

Store commonly queried values in typed columns as well as retaining the raw record JSON where practical.

For example:

```sql
CREATE TABLE raw_app_usage (
    logger_record_id        INTEGER PRIMARY KEY,
    logger_import_file_id   INTEGER NOT NULL,
    source_record_index     INTEGER,

    event_timestamp_utc     TEXT,
    package_name            TEXT,
    app_name                TEXT,
    event_type              TEXT,
    duration_ms             INTEGER,

    ingested_at_utc         TEXT NOT NULL,
    raw_record_json         TEXT NOT NULL,

    FOREIGN KEY (logger_import_file_id)
        REFERENCES logger_import_file(logger_import_file_id)
);
```

The exact schema must reflect the actual logger JSON rather than inventing unavailable values.

Do not convert UTC source timestamps to Adelaide or other local time during ingestion.

Store source times in UTC. Local-time rendering and calendar-date interpretation belong in later processing or display layers.

# 16. Unknown record handling

The importer must not fail an entire file merely because it contains a record type that is not yet understood.

When `allow_unknown_record_types` is true:

1. Store the record in `raw_unknown_record`.
2. Preserve the complete JSON.
3. Record its detected type if available.
4. Add a warning message.
5. Continue processing the rest of the file.

Example table:

```sql
CREATE TABLE raw_unknown_record (
    logger_record_id        INTEGER PRIMARY KEY,
    logger_import_file_id   INTEGER NOT NULL,
    source_record_index     INTEGER,

    detected_record_type    TEXT,
    source_timestamp_utc    TEXT,

    ingested_at_utc         TEXT NOT NULL,
    raw_record_json         TEXT NOT NULL,

    FOREIGN KEY (logger_import_file_id)
        REFERENCES logger_import_file(logger_import_file_id)
);
```

When `allow_unknown_record_types` is false, mark that file as failed but continue with other files unless `stop_on_file_error` is enabled.

# 17. JSON discovery and parsing

The handler should support the actual formats produced by LifePIM Logger.

The parser should recognise at least:

* One JSON object per file.
* A JSON array of records.
* A wrapper object containing one or more record arrays.
* Newline-delimited JSON, if current logger files use it.

Do not rely exclusively on file naming conventions to determine record type.

Use, in order:

1. Explicit record-type fields in the JSON.
2. Known root-property names.
3. Known field signatures.
4. Filename hints only as a fallback.

The parser should return a common internal record structure such as:

```python
ParsedLoggerRecord(
    record_type="app_usage",
    timestamp_utc="2026-08-06T12:34:56Z",
    payload={...},
    source_index=42,
)
```

Malformed files must produce a useful error including:

* File path.
* JSON parsing error.
* Line and column where available.
* Whether any records were committed.

# 18. Transaction behaviour

Process each file within its own target-database transaction.

Recommended behaviour:

```text
Begin transaction for one source file
    ↓
Insert logger_import_file row
    ↓
Parse and insert all records
    ↓
Update file counts
    ↓
Commit
```

On file failure:

```text
Rollback the file transaction
    ↓
Write a failed logger_import_file result if practical
    ↓
Record the failure in LifePIM process history
    ↓
Continue with the next file
```

A broken file must not cause successfully completed earlier files to be rolled back.

Do not use one enormous transaction for an entire folder.

# 19. Incremental import behaviour

The normal **Run** action performs an incremental import.

Steps:

1. Validate configuration.
2. Confirm source folder exists.
3. Create target directory if permitted.
4. Open or create logger database.
5. Apply logger database migrations.
6. Scan matching files.
7. Register discovered files.
8. Determine whether each file is new, changed or already imported.
9. Skip unchanged previously imported files.
10. Parse and import new or changed files.
11. Commit each successful file independently.
12. Optionally move successful files.
13. Record file-level results.
14. Finalise run counts and status.

If a file has the same content hash as an already imported file:

* Skip the file.
* Mark it clearly as a duplicate.
* Do not insert its records again.

If the same path now contains different content:

* Treat it as a changed source file.
* Import it as a new file version.
* Do not delete records from the previous version automatically in incremental mode.

A later data-maintenance feature may provide source-version reconciliation. It is not required here.

# 20. Rebuild behaviour

Provide a separate **Rebuild Database** action.

Rebuild is destructive to the process-owned logger database contents and must require explicit confirmation.

Confirmation text should clearly state:

```text
This will recreate the logger database tables and re-import all recognised JSON files from the configured source folder.

The original JSON files will not be deleted.
```

Rebuild steps:

1. Validate configuration.
2. Confirm user approval.
3. Create a rebuild process run.
4. Close existing logger database connections.
5. Create a temporary replacement database in the same data directory.
6. Apply current schema migrations.
7. Import all matching source files into the temporary database.
8. If the rebuild completes successfully:

   * Close connections.
   * Rename the existing database to a timestamped temporary backup.
   * Replace it with the new database atomically where possible.
   * Remove the temporary backup only after the replacement opens successfully.
9. If the rebuild fails:

   * Preserve the existing working logger database.
   * Preserve the failed temporary database for diagnosis, or remove it according to existing project conventions.
   * Mark the run failed.
10. Do not move source files during rebuild unless this behaviour is explicitly designed and tested.

Do not delete the existing logger database before a successful replacement is ready.

A simpler in-place rebuild is acceptable only if the application already has a reliable SQLite backup and replacement utility. Prefer the safe replacement approach.

# 21. Move-after-success behaviour

When configured with:

```text
successful_file_action = move
```

After a file’s database transaction commits successfully:

1. Ensure the processed folder exists.
2. Preserve relative subfolder structure when recursive scanning is enabled.
3. Avoid overwriting a different existing file.
4. Add a timestamp or hash suffix when a name collision occurs.
5. Update the process file record with the resulting location.
6. Log the move result.

If moving fails after import succeeds:

* Do not roll back the imported database records.
* Mark the file result as `warning`.
* Leave the source file in place.
* Ensure the next incremental run recognises it as already imported and does not duplicate the records.

# 25. Preview functionality

Preview must not:

* Create the logger database.
* Modify the logger database.
* Insert process records other than an optional preview run record.
* Move files.
* Rename files.
* Delete files.
* Mark files as imported.

Preview should:

1. Validate paths and configuration.
2. Scan matching files.
3. Inspect enough JSON to identify file formats and record types.
4. Compare files with existing process-file history.
5. Estimate new, duplicate and changed files.
6. Estimate record counts where reasonably possible.
7. Report unknown or invalid files.


For very large files, preview may sample or stream records. It should not read all data into memory.

Clearly label counts as estimates when they are not exact.

# 33. Security and privacy

All processing is local.

Requirements:

* Do not send source files or logger records to external services.
* Do not use cloud APIs.
* Do not add telemetry.
* Do not include raw location coordinates in general application logs.
* Do not include complete JSON payloads in user-visible error messages unless the user explicitly opens a raw-record diagnostic view.
* Treat the logger database as private LifePIM data.
* Use the existing LifePIM data-directory and backup conventions.

---

# 34. Performance requirements

The importer should:

* Stream large JSON arrays where practical.
* Avoid loading entire multi-megabyte files into memory unnecessarily.
* Batch inserts using SQLite transactions.
* Use prepared statements or executemany-style insertion.
* Commit per file.
* Keep the UI responsive.
* Update progress periodically rather than once per record.
* Avoid calculating hashes repeatedly for unchanged files.
* Create indexes after bulk rebuild where that materially improves rebuild speed.

Version 1 does not require parallel file processing.

Reliable, traceable processing is more important than maximum throughput.

---

# 35. Timestamp rules

Store all imported logger timestamps in UTC where the source supports UTC.

Store all process-framework timestamps in UTC.

Do not convert records permanently to Adelaide time during import.

The later normalisation, aggregation or calendar-generation process may derive:

```text
local_timestamp
local_date
timezone_name
UTC offset
```

based on the user’s location or relevant timezone.

The raw database must preserve the original timestamp and original raw JSON.

# 42. Implementation guidance

Prefer a small, explicit and reliable framework.

Do not attempt to make every part of processing configurable.

The reusable boundary is:

```text
LifePIM process framework
    manages definitions, execution and history

Process handler
    performs one known kind of work
```

For this version, the only fully implemented handler is:

```text
logger_json_import
```

A user should be able to configure the source folder, preview the files, press **Run**, and then inspect exactly what files and records were loaded into `logger.sqlite`.

The result should establish the foundation for later logger processing without turning LifePIM into a general-purpose enterprise ETL platform.
